## Triage

**Verified:**

- **Partial seam and repeated mode checks.** `detect_tracker` already centralizes selection, and `fetch_issue`, `list_issues`, `open_blockers`, and `comment` share entry points. `local_issue` already supplies a common issue record shaped like the GitHub response. A search for issue and ticket operations in the job commands, other factory commands, and Hub's project reader found no existing intent-level adapter interface. There are 58 source lines containing `GITHUB` in `job`. The count includes branch and PR handling as well as tracker operations.
- **Different mutation semantics.** `set_status` edits one Markdown field. `label` uses `add` to replace that field in local mode and only honors `remove` on GitHub. A temporary fixture ran the extracted functions with the existing fake `gh`: removing `ready-for-agent` kept both the status and the `factory` label locally, while the fake GitHub issue retained only `factory`. This proves the interface divergence. The completion paths already compensate for it, so the experiment establishes neither a live GitHub result nor a broken completion workflow.
- **Completion and merge have different responsibilities.** `advance` repeats tracker-specific completion handling for merged jobs and protected changes completed by hand. It calls `set_status` and `commit_ticket` locally, and label removal and `close_issue` on GitHub. `is_merged` instead checks PR state or verifies that the local branch has work and is an ancestor of the base. `cmd_merge` also branches for GitHub push, PR readiness, CI and merge versus a local Git merge. The ticket branches in `advance` can move behind the tracker interface. The merge workflow keeps its own mode checks.
- **The testing dependency is real.** `new_gh_repo` installs a fake `gh` with JSON issue and PR state and sets up a temporary origin. The GitHub clean-merge and hand-merge tests rely on it and check issue closure. An in-memory adapter can replace that setup for ticket behavior exercised through the lifecycle. GitHub command behavior still merits its own coverage.

**Recommendation:** ready-for-agent. The maintainer resolved ownership of Git and PR operations and confirmed the existing Open work queries. The Ticket effect interface gives ticket 04, Job lifecycle, a seam it can use when it separates Progression checks from effects.

## Agent Brief

**Category:** enhancement

**Summary:** Route Ticket effects through a shared interface with GitHub, local Markdown, and in-memory adapters.

**Current behavior:**

`detect_tracker` selects the mode, and helpers such as `comment` already share entry points. `label` exposes GitHub label arguments even though local Markdown uses a single `Status` field. `advance` handles the done Ticket effect separately in each mode for merged jobs and protected changes completed by hand. GitHub lifecycle tests use `new_gh_repo` to provide a fake `gh` and JSON issue and PR state.

**Desired behavior:**

Job commands request a Ticket effect in terms of what happened. The tracker adapter makes the corresponding write and preserves the existing user-visible outcome, including the factory comment format, unrelated labels, and local ticket commit rules. A done effect can complete an issue GitHub already closed during merge. If GitHub refuses the existing close operation, preserve the warning behavior.

`advance` keeps the existing Progression checks and requests the done effect after merge verification succeeds, or when a protected change is recorded as completed by hand. The merge workflow still checks PR state or local branch ancestry and performs the merge. Feature completion uses the existing Open work queries.

**Key interfaces:**

- **Ticket effect interface.** Accept a ticket reference and the intent to wait on a human, mark done, reject, or post a comment. Carry the reason, comment, or prior waiting state when the effect needs it. Callers express that context without supplying GitHub label mutations or Markdown field edits.
- **Tracker selection.** `detect_tracker` continues to honor explicit config, the tracker document, and the origin fallback in that order. Preserve the configured triage label mapping and existing ticket identifiers.
- **Lifecycle and merge.** `advance` calls the shared Ticket effect interface for ticket writes in scope. `is_merged` and `cmd_merge` stay in the merge workflow. `open_work_for` retains its current queries.
- **In-memory adapter.** Exercise the same Ticket effect interface as production. A lifecycle test can observe the resulting ticket state and comments without invoking a command or loading a fake GitHub issue.

**Acceptance criteria:**

- [x] With an explicit tracker setting, conflicting tracker documentation, or only an origin, the same production adapter is selected as before. Existing GitHub issue numbers and local ticket identifiers still resolve.
- [x] A waiting-on-a-human effect uses the configured waiting label and removes the queue label on GitHub. Local Markdown records the configured waiting status. Both preserve unrelated labels and retain existing factory comment formatting when a comment is posted.
- [x] A successfully verified merge and a protected change completed by hand each request the same done effect in both modes. GitHub removes the applicable queue and waiting labels, posts the completion comment, and closes an open issue. An already-closed issue requires no close command, and a refused close still reports a warning. Local Markdown records `done`, posts the completion comment, and commits the ticket only under the existing ticket commit rules.
- [x] An ordinary rejection still records the configured `wontfix` outcome in both modes and retains the rejection comment. A comment-only effect leaves triage labels and local `Status` intact.
- [x] A failed merge Progression check prevents the done Ticket effect. The merge workflow still uses PR state for GitHub and branch ancestry for local merges.
- [x] For a feature with otherwise equivalent open tickets, GitHub Open work includes issues matching any of the four configured triage labels and excludes an open issue with none of them. Local Open work includes an open ticket outside those four statuses. Closed tickets and tickets targeting another feature remain excluded in both modes.
- [x] Lifecycle tests cover the done and waiting-on-a-human effects through the in-memory adapter without a `gh` executable or JSON issue fixtures. Production adapter tests cover GitHub command behavior and local Markdown writes.

**Out of scope:**

- PR state, merge verification and execution, branch operations, and CI.
- Changes to which tickets count as Open work, or redesigns of queue lookup, blockers, or other ticket reads.
- Extracting the job lifecycle module, changing Progression checks or Verdicts, and changing supported ticket formats.
