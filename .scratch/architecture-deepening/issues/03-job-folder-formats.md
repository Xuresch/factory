## Triage


**Verified:**

- `job` already has `first_line`, `header`, and `section` for basic Markdown reads. `sync`, `review_table`, and `next_review` still repeat the same review verdict regex. `stuck_disputes` and `friction` compare exact strings. In a temporary fixture, the current Python regex read `VERDICT:  CHANGES` as `CHANGES` and the exact comparison returned false. `review_problem` also validates required sections and, when given the active job, checks findings and responses.
- `gate` and `hook` each decode `job.json` directly, as does `route.main` after it calls `job sync`. `gate.reusable` has its own checks-header parser. The cited `protected_changes` function reads the Git diff and configuration. `job.load` already pairs JSON decoding with lock handling, `save` atomically replaces the document, and `peer_jobs` deliberately reads without taking a lock. These are existing pieces of the implementation. The readers have no shared job-files module.
- `report.read_jobs` decodes job documents separately and takes a text-and-hash snapshot of Markdown for transport. `report.build` keeps the previous state if a job document cannot be decoded as an object. The claim that every reader independently interprets Markdown is too broad. The reporter forwards it without interpreting verdicts. The dashboard command's `subscriptions` function also has a direct JSON read for cost fields.
- Rust `project` collects round numbers from the job document, stage history, and artifact names. It joins review files with `review_log` and uses `verdict` for both gate and review first lines. Standalone `roundVerdicts` reads the files with `verdictOf` and reads the Rust projection in hub mode. Drawer `tone` maps first lines to colors and also recognizes other artifact kinds. The Rust tests use inline documents and first lines. There is no shared Python/Rust fixture for these rules.
- An experiment used the current Python, Rust, and JavaScript parser expressions and functions with temporary job artifacts. Rust and standalone JavaScript read `GATE: PASS` and `VERDICT: FAIL` as verdicts even when the content came from review files. The Python review regex rejected both. For a checks file with `REPORT: ready` on the first line and `GATE: PASS` on the second, the Python header reader returned `PASS` and both display readers returned `invalid`.

**Recommendation:** ready-for-agent. The maintainer settled which first lines count, what the dashboards show, and which readers share fixtures. The job-files module can own format interpretation while callers retain their existing read and write behavior.

## Decisions

- **2026-11-20.** Read the Verdict only from the artifact's first line. Allow whitespace after the colon. Review artifacts require `VERDICT:` with `PASS` or `CHANGES`. Checks artifacts require `GATE:` with `PASS` or `FAIL`. A missing artifact is pending. A present artifact with an unreadable or invalid first line is invalid. A later `GATE:` header never supplies a Verdict. Old jobs with that format no longer run through the lifecycle.
- **2026-11-20.** Both dashboards show the declared Verdict. The Progression check, currently implemented by `review_problem`, is a separate lifecycle judgment owned by ticket 04.
- **2026-11-20.** Include the standalone dashboard's Verdict read in the shared job-folder fixtures. Keep `tone` focused on presentation. The dashboard command's subscription scan belongs with tickets 01 and 06.

## Agent Brief

**Category:** enhancement

**Summary:** Centralize Python job-folder reads and verify the same declared Verdict contract in Python, the Rust hub projection, and the standalone dashboard.

**Current behavior**

`job` mixes a repeated review regex with exact-string comparisons and reads a gate's Verdict from its Markdown header block. Gate reuse parses that block separately. The hub and standalone dashboard read the first line and accept either prefix and any of the three values for either artifact kind. The Python commands decode job documents independently, and the reporter transports Markdown and hashes its raw bytes.

**Desired behavior**

The Python job-files module handles job document decoding, Markdown format reads, and declared Verdict parsing. All round Verdict callers use its format rules. A review starts with `VERDICT:` and declares `PASS` or `CHANGES`. Checks start with `GATE:` and declare `PASS` or `FAIL`. Whitespace after the colon is allowed. A missing artifact is pending. An existing artifact with an empty, unreadable, or malformed first line is invalid, even if a later line declares a Verdict.

The hub projection and standalone dashboard apply the same rules and display the declared Verdict. Job progression continues to use `review_problem` to validate the parsed Verdict against the review and active job. Gate reuse requires a declared `PASS`, the same commit and checks script, and a script that runs identically in round and merge modes.

The module keeps reads usable by both lock-taking and lock-free callers. The reporter can still read text and hash the original bytes, and an unreadable, partial, or non-object job document retains the previous reported snapshot when one exists. Routing still uses synchronized intake to choose agents and prints the selection after recording it.

**Key interfaces**

- The Python job-files module gives `job`, `gate`, `route`, and `report` one way to read the job document and the job fields each caller needs. Its Markdown reads supply declared round Verdicts, checks metadata, headers, and named sections. Its snapshot reads support the reporter's text and raw-byte hashes.
- The Verdict read takes the artifact kind and distinguishes a missing artifact, an invalid first line, and a valid declaration. `sync`, `next_review`, review summaries, dispute checks, and gate reuse share this read.
- Rust `project` and standalone `roundVerdicts` apply the artifact-specific Verdict rules to their inputs. Historical round and reviewer associations still come from round artifacts and recorded reviewer assignments. `tone` maps values to presentation.
- `review_problem` consumes the parsed review Verdict and continues to make the Progression check, including validation of required sections, findings, and responses.

**Acceptance criteria**

- [ ] Exercise `job`, the normal and hook gate commands, `route`, and `report` with the same valid job document. Each reads through the shared Python module, and gate and route get their fields without decoding the document themselves.
- [ ] Run Python, Rust, and standalone dashboard tests against the same job-folder fixtures and expected declared Verdicts. Cover both allowed values for each artifact kind, whitespace after the colon, missing artifacts, empty and unreadable first lines, wrong prefixes, and disallowed values. A checks artifact with a valid `GATE:` header only on its second line is invalid in all three. Include a historical round with a recorded reviewer assignment.
- [ ] A validly declared `PASS` review with a required section missing displays `PASS` in both dashboard modes and fails the Progression check. A `VERDICT:  CHANGES` review with valid findings is read as `CHANGES` consistently by synchronization, review summaries, progression, and dispute checks.
- [ ] Gate reuse succeeds for a passing checks artifact with matching commit and script metadata and an eligible script. It refuses reuse for a later-only `GATE:` header, changed commit, changed script, or a script that uses the round-versus-merge mode.
- [ ] Incremental reporting preserves text and raw-byte hashes for valid inputs and sends no replacement for an unreadable, partial, or non-object job document with a previously reported snapshot.
- [ ] While a command holds the job lock, a lock-free reader can still read a complete document. Job writes replace the document atomically. `route <job-id>` continues to record and print the selected agents through its existing entry point.

**Out of scope**

- Lifecycle redesign and changes to Progression check policy or Ticket effects. Ticket 04 owns lifecycle work.
- Dashboard presentation changes and the dashboard command's subscription scan. The scan belongs with tickets 01 and 06.
- Folding the `route` command into `job`, migrating historical job folders, and accepting a Verdict below the first line.
