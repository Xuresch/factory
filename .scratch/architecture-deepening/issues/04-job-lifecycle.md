# 04: Job lifecycle decides the next stage

**Status:** ready-for-agent

**Category:** enhancement

**Blocked by:** 02 (Tracker seam), 03 (Job folder formats)

**What to build:** Give the lifecycle module one decision interface for the current job, its parsed reports, and any observed worktree or tracker facts. Use that decision to recommend the next action and to validate and apply a requested transition. Return the destination, the reason, and the effects to execute. This gives callers leverage through a small interface and gives maintainers locality when stage rules change.

- [ ] On a stable job snapshot whose transition prerequisites are satisfied, the stage recommended by `job next` is accepted by `job advance`. Keep the explicit target argument as a check against the current decision and preserve the existing manual commands.
- [ ] Table tests cover gate PASS, gate FAIL with and without rounds left, review PASS, review CHANGES with rounds left, exhausted rounds, and unresolved review disputes. Missing, stale, or malformed gate results prompt a gate rerun. None consumes a build round.
- [ ] Gate, review, and merge recovery share the round-availability rule. A review dispute can escalate before the round limit, a recoverable merge failure can send the job back to build, and UI fallback can still take the last available repair round. Rewind preserves a higher existing round limit and grants at least the configured allowance.
- [ ] The decision can be tested without tracker writes, worktree changes, or notifications. Test effect execution separately and retain command-level coverage for persisted transitions, merge-only carryover, holds, and recoverable effect failures.

## Triage

**Verified:**

- `next_intake`, `next_spec`, `next_build`, `next_gate`, and `next_review` select destinations from reports or job state. `advance` repeats the corresponding decisions and performs further checks, including worktree cleanliness and commit identity. The claim that every `next_*` repeats transition policy is too broad. `next_merging` waits for CI or delegates to `job merge`, and `next_slices` schedules slice work. `next_approve` recommends the merge command on APPROVE, which calls `advance` when entering merging.
- `after_round` shares retry selection between `next_gate` and `next_review`. The gate and review branches in `advance` independently check whether the current round is the last, and `cmd_merge.back` does the same for recoverable merge failures. The dispute check in `after_round` cannot change a gate decision today because `stuck_disputes` only applies in review. `maybe_fall_back` asks whether the *next* round is the last, and `cmd_rewind` extends the round limit. Both are related policies with distinct semantics.
- A temporary fixture with a current-commit check report declaring `GATE: UNKNOWN` made `next_gate` recommend `advance … build`. The same report made `advance` refuse with `the gate passed`. The experiment ran the existing functions with a stubbed HEAD and no mutation of repo or tracker state.
- `advance` interleaves legality checks with round updates, tracker comments and labels, worktree setup and cleanup, and `announce`. `cmd_rewind` assigns the stage directly and performs its own effect sequence. The redundancy check found `TRANSITIONS` for allowed stage pairs, `after_round` for advice, and `next_round` for initializing a new round. Together they cover parts of the requested interface. There is no shared decision used by both advice and application. Existing coverage such as `t_next_gate_fail_partial_paused`, `t_last_round_goes_to_fallback`, and `t_merge_conflict_goes_back_to_builder` exercises these rules through command sequences.

**Recommendation:** ready-for-agent. The existing commands and successful transitions define the contract, and the malformed gate fixture identifies one mismatch with a concrete resolution. The decision is in-process once job-folder reports and external observations have been read. Tickets 02 and 03 provide the tracker seam and report formats that the lifecycle implementation needs.

## Agent Brief

**Category:** enhancement

**Summary:** Use one lifecycle decision for stage advice, transition validation, and the effects of applying a transition.

**Current behavior:** Stage-specific advice picks a target, and `advance` derives much of the same policy again while executing tracker and worktree operations. Merge recovery chooses its own destination, and rewind assigns its destination directly.

**Desired behavior:** For a job and its parsed reports, the lifecycle module accepts the current intent and any observations needed for that intent, then returns the applicable action, stage, or refusal and the effects for a transition. Live prerequisites are checked again when applying a decision. The current explicit transition target is checked against that decision. Worker scheduling, CI waits, and manual paths keep their existing behavior. A malformed current gate result takes the same rerun path as a missing or stale result.

**Key interfaces:**

- The lifecycle decision consumes the current stage, round budget, parsed job-folder reports, and relevant observations such as commit identity. It returns the reason for a transition or refusal along with any effects needed to apply it.
- `next_steps` uses that decision for stage advice. `advance` uses it to validate the explicit target and execute the resulting effects through the existing effect adapters and operations.
- `cmd_merge` supplies the merge outcome. `cmd_rewind` supplies the requested destination and uses the lifecycle rules for rewind eligibility and round allowance.

**Acceptance criteria:**

- [ ] For the same facts, table tests assert the destination and reason used by advice and validation. Cover gate and review verdicts, stale or malformed gate reports, review disputes, and the round limit.
- [ ] A recoverable merge failure with a round left opens exactly one build round. The same failure with an exhausted allowance escalates. The UI fallback retains its last-repair-round behavior, and rewind grants its existing allowance without lowering a higher limit.
- [ ] Command tests preserve explicit approval, rejection, feedback, and rewind. Keep coverage for clean-worktree and same-commit checks, merge-only carryover, and a hold that records paused before work resumes.
- [ ] Decision tests need no tracker, subprocess, or notification calls. Effect tests cover ordered execution and existing failure handling, including worktree setup before posting acceptance and notification failure after a valid transition.

**Out of scope:**

- CLI syntax changes, new stages, and changes to configured retry or fallback limits.
- Rebuilding tracker adapters or changing persisted job-folder formats.
- Redesigning worker scheduling, slice execution, or the merge retry and CI wait mechanisms.
